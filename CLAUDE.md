This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

xv6 — a teaching OS for RISC-V — extended for os262 Assignment 3. The assignment adds two new syscalls (`flip_display` and `map_display`) that expose the virtio-gpu framebuffer to user processes. Both syscalls have stub implementations in `kernel/sysproc.c` with `TODO` comments marking the work.

## Build and run

Requires a RISC-V toolchain (`riscv64-unknown-elf-*` or `riscv64-linux-gnu-*`) and `qemu-system-riscv64`. The recommended environment is the devcontainer (VS Code → "Reopen in Container").

```sh
make qemu         # build and boot in terminal (serial on stdio, GPU window in QEMU)
make qemu-web     # boot with noVNC viewer at http://localhost:6080/vnc.html
make qemu-gdb     # boot suspended, waiting for GDB on port from GDBPORT
make clean        # remove all build artefacts
```

Run user tests inside xv6:
```
$ usertests         # full test suite
$ show_flip Hello   # test flip_display syscall
$ show_map          # test map_display syscall (interactive)
$ gol               # Game of Life (flip or map mode)
$ gol map
```

## Assignment: the two new syscalls

Both stubs are in `kernel/sysproc.c` and currently `return -1`.

**`sys_flip_display`** (SYS 22) — zero-copy page flip.
- Arg 0: user VA of a page-aligned buffer, exactly `GPU_FB_PAGES * PGSIZE` bytes (640×480×4 = 1,228,800 bytes).
- Should re-point the GPU resource's backing pages to the caller's physical pages — no pixel copy.
- Used by `user/show_flip.c` and `user/gol.c` (flip mode).

**`sys_map_display`** (SYS 23) — map kernel framebuffer into user space.
- Arg 0: desired page-aligned user VA, or 0 to auto-select above `p->sz`.
- Should install `GPU_FB_PAGES` PTEs with `PTE_U|PTE_R|PTE_W` pointing at the kernel's `fb[]` pages in `virtio_gpu.c`.
- Returns the mapped VA on success, `(uint64)-1` on failure.
- Used by `user/show_map.c` and `user/gol.c` (map mode).

## Architecture

### Boot and kernel init (`kernel/`)
- `entry.S` / `start.c` — machine-mode entry, switch to supervisor mode, call `main()`
- `main.c` — initialises all subsystems in order; calls `virtio_gpu_init()` which sets up the 640×480 framebuffer and draws "Hello World", then spawns `display_daemon` (periodic flush ~60 fps)
- `vm.c` — page-table management; `kvmmake()` identity-maps VIRTIO1 alongside UART/disk/PLIC

### Memory layout (`kernel/memlayout.h`)
- `KERNBASE = 0x80000000`, `PHYSTOP = KERNBASE + 128 MB`
- `TRAMPOLINE` at top of VA, `TRAPFRAME` one page below it
- `GPU_FB_PAGES = 300` pages for the 640×480×4-byte framebuffer

### Syscall path
- Numbers in `kernel/syscall.h`; dispatch table in `kernel/syscall.c`
- User stubs generated by `user/usys.pl` → `user/usys.S`
- User-facing declarations in `user/user.h`

### virtio-gpu (`kernel/virtio_gpu.c`)
- MMIO at `VIRTIO1 = 0x10002000` (bus.1, separate from virtio-disk on bus.0)
- Allocates `fb[]` — `GPU_FB_PAGES` physical pages via `kalloc()` — on init
- Commands used: `RESOURCE_CREATE_2D`, `RESOURCE_ATTACH_BACKING`, `SET_SCANOUT`, `TRANSFER_TO_HOST_2D`, `RESOURCE_FLUSH`
- Pixel format: `B8G8R8X8_UNORM` (little-endian: bits[7:0]=B, [15:8]=G, [23:16]=R)
- `display_daemon` runs in a kernel thread and flushes the framebuffer on every timer tick

### Process / VM helpers relevant to the assignment
- `kernel/vm.c`: `mappages()`, `uvmalloc()`, `walkaddr()` — use these to manipulate user page tables
- `kernel/proc.h`: `struct proc` has `pagetable` and `sz` fields
- `kernel/kalloc.c`: `kalloc()` / `kfree()` for physical pages
